# 子 Agent 协作协议

> **定位**：本文件规范「**主会话做检查、设计、反馈与决策；实际开发由子 Agent 承担**」的协作模式。
> 与 `docs/develop.md` 的关系：develop.md 定义**工程流程**（分支/TDD/门禁/审查），本文件定义**任务如何分发与验收**；
> 冲突时以 develop.md 为准。与 `docs/plans/collaboration-template.md` 的关系：那份规范「多个开发者的文件所有权」，
> 本份规范「主会话 ↔ 子 Agent 的上下文边界与验收协议」。
>
> **元规则**：本文件本身是流程文档，修订须经人类审查（develop.md 约束 2）。

---

## 0. 为什么要这个模式

**问题**：单个长会话把「读代码、写代码、跑测试、排查、写文档」全做完，上下文被实现细节占满——
到后期主会话看不见全局，人类也难以聚焦在「检查/决策」上。

**分工原理**：子 Agent 的产出**只有报告回到主会话**（结构化文本，几 KB），而它读的代码、写的实现、
跑的测试都留在它自己的上下文里。主会话因而始终保有三个能力：**看全局、做判断、下决策**。

**收益的边界（重要）**：子 Agent 只省「代码正文」的上下文，
**不省**「做了什么/改了哪些文件/测试结果/遇到的问题」——这些必须以摘要形态回到主会话，否则无法验收。

---

## 1. 角色与职责

| 角色 | 承担者 | 职责 | **不做** |
|---|---|---|---|
| **主会话**（编排） | 当前会话 | ① 读文档与代码、理解需求；② **设计**方案与接口；③ **检查**子 Agent 产出并反馈；④ 向人类**报告**与请示**决策**；⑤ 维护文档与进度 | 不写业务实现（除非人类明确要求） |
| **子 Agent**（实现） | `Agent` 工具派发 | ① 按任务书实现代码与测试；② 自测全绿；③ 提交 commit；④ 返回结构化报告 | 不改需求/设计文档；不碰他人所有权文件；不擅自扩大范围 |
| **人类** | 用户 | ① 审批设计变更（约束 2）；② 裁定设计缺口；③ 里程碑验收（约束 10）；④ 检查 demo | — |

## 2. 工作循环

```
LOOP（每个工作包一轮）：
  1. 主会话：读现状（文档 + 代码）→ 识别工作包 → 产出「实现任务书」（§3 模板）
  2. 主会话：派发子 Agent（一包一 Agent；可并行的包同时派发，见 §4）
  3. 子 Agent：实现 + 自测 + commit → 返回报告（§5 格式）
  4. 主会话：**验收**（§6 协议：不信自报，重跑门禁 + 抽查）
        ├─ 通过 → 合入（约束 9 合并规程）→ 更新进度文档 → 回报人类
        └─ 不通过 → 附失败详情**重派**（最多 2 次；仍失败则记录阻塞并请人类裁定）
  5. 主会话：向人类汇报（§7 格式）→ 人类决策 → 回到 1
```

**上下文节约的关键**：第 1 步的任务书要**自包含**（子 Agent 不必自己摸全局）；
第 4 步的验收以**命令输出**为准（不读实现全文，只抽查关键点）。

## 3. 实现任务书模板（主会话填写）

```markdown
## 任务：<一句话目标>

### 背景与目标
<为什么做这个；完成后什么会变好。2-3 句>

### 必读（按序，自包含）
1. 任务文件：docs/tasks/<NN>-<slug>.md 的 <子任务编号与原文>
2. 设计依据：docs/detail-design.md <§章节>（接口签名以此为准）
3. 需求条目：docs/proposal.md <FR 编号>
4. 流程约束：docs/develop.md（约束 6 质量 / 约束 9 分支与合并规程）
5. 既有参考实现：<同类能力的文件路径，供风格对齐>

### 交付物（逐条可勾）
- [ ] <文件 1>：<要点>
- [ ] <文件 2 测试>：<必须覆盖的用例方向>
- [ ] 任务文件勾选：docs/tasks/<NN>.md 的 <具体 checkbox 文本>

### 硬约束
- **允许改动**：<文件白名单>
- **禁止改动**：<文件黑名单：需求/设计/其他任务文件/progress.md/scripts 等>
- 命名空间/接口边界：<如 `x.<script>.<name>`；不得新增公共导出面>
- 提交粒度：一个子任务 = 一个 commit（Conventional Commits + 模块号）
- **自测门禁**：`pnpm test` / `pnpm typecheck` / `pnpm lint` / `node scripts/validate-docs.mjs` 全绿方可交付

### 完成定义
- <可验证的判据 1>
- <可验证的判据 2>

### 返回报告（唯一输出）
按 §5 格式。
```

**填写要点**：
- **必读清单必须自包含**——子 Agent 不应需要「自己去找」上下文；
- **文件白名单要精确**——这是防止多 Agent 冲突的主要手段（§4）；
- **完成定义要可验证**——「测试全绿」比「实现正确」可判。

## 4. 并行与隔离

### 可并行的判据（三条全满足）

1. **文件不重叠**（任务书的文件白名单两两无交集）；
2. **无数据依赖**（不需要对方的产出才能开工）；
3. **各自可独立验证**（有独立的完成定义）。

任一条不满足 → **串行**。

### 隔离方式

| 方式 | 何时用 | 说明 |
|---|---|---|
| **同一工作区串行** | 默认（简单、无额外成本） | 一次只派一个子 Agent；主会话在其间验收 |
| **`git worktree` 并行** | 确需并行且文件白名单不重叠 | 每 Agent 独立工作区 + 独立分支；**代价：每个 worktree 需 `pnpm install`（约 195MB 依赖）** |

**隔离的硬性要求**（无论哪种方式）：
- 子 Agent **只在自己的文件白名单内写**；
- 跨所有权改动（改他人的文件或公共契约）**必须先报主会话**，由主会话裁定后再动；
- **一个工作区同时只有一个子 Agent 在写**（避免文件互相覆盖）。

### 并行的常见陷阱

- **公共类型文件**（如 `types.ts`）是天然冲突点——若两包都要改它，改为串行（或让其中一包先做、另一包基于其结果）；
- **测试文件与实现同包**——文件白名单要同时覆盖实现与测试路径；
- **fixtures 共享**——两包都要加夹具数据时，数据文件是冲突点，同样按串行处理。

## 5. 子 Agent 返回报告格式（唯一输出）

```text
STATUS: DONE | BLOCKED | SPEC_CONFLICT

## 完成的子任务
- <任务书 checklist 原文>（逐条）

## 改动文件
- <路径>：<一句话说明>（新增/修改）

## commit 列表
- <hash> <标题>

## 测试证据
- 新增/更新用例：<文件>（<N> 例）
- 自测结论：`pnpm test` <X> 文件 / <Y> 用例；typecheck / lint / validate-docs <结果>

## 遇到的问题与决策（若有）
- <问题> → <如何解决/为何这样选>

## 若是 BLOCKED / SPEC_CONFLICT
- 原因：<...>
- 已尝试：<...>
- 建议的最低人工介入点：<...>
```

**要求**：
- **不贴代码正文**（需要时主会话自己读关键文件）；
- **测试数字必须来自真实执行**（不是估计）；
- `SPEC_CONFLICT` 时**立即停止**，不猜测、不顺手改文档。

## 6. 验收协议（主会话执行，不信自报）

| # | 检查 | 做法 |
|---|---|---|
| 1 | **重跑门禁** | 亲自执行 `pnpm test` / `pnpm typecheck` / `pnpm lint` / `validate-docs`，以输出为准 |
| 2 | **一致性核对** | `git log` 中该包的 commit 数 == 子任务完成数 == 任务文件勾选数 |
| 3 | **反糊弄抽查** | 抽 1–2 个关键测试**读断言**——必须针对行为（状态变化/返回值/事件序列），禁止空断言与纯快照 |
| 4 | **红线扫描** | engine 范围 grep `eval(` / `new Function` / `document.` / `window.` / `fetch(`；命中即验收失败 |
| 5 | **范围核对** | `git diff --stat` 的文件列表 ⊆ 任务书白名单；越界即验收失败 |
| 6 | **玩家视角复核**（涉及玩家可见能力时） | 该能力是否有 **L2 层效果断言**（`packages/runtime-ui/test/acceptance/`）？没有则要求补——这是抓「宿主装配缺口」的唯一有效层（见 `docs/plans/open-items.md` L-1） |

第 6 条是**本项目特有**的验收项，源自 6 例「引擎就绪但玩家点了没反应」的宿主装配缺口——
**引擎单测与加载器诊断都覆盖不到这一层**。

---

## 7. 向人类汇报的格式

```markdown
## 本轮完成
- <工作包>：<一句话成果>（commit <hash 范围>，PR #<N>）

## 验收证据
- 测试：<X> 文件 / <Y> 用例绿；四门禁 + validate-docs <结果>
- 关键断言：<1-2 条最能说明「真的做对了」的>

## 发现的问题（需你裁定）
- <问题> → 我的建议 → 你的选项

## 遗留
- <登记在 docs/plans/open-items.md 的条目>
```

**汇报要点**：先给结论（做完了什么、能不能用），再给证据，最后给需要人类决策的事项。

---

## 8. 反模式（明确禁止）

| 反模式 | 为什么禁止 |
|---|---|
| 子 Agent 报告「测试全绿」但实际没跑 | 验收协议第 1 条兜底（主会话重跑） |
| 主会话读子 Agent 的全部 diff 来「确认」 | 违背上下文节约的初衷；应靠抽查 + 门禁 + 覆盖闭环 |
| 同一工作区并行两个子 Agent | 文件互相覆盖，且故障难归因 |
| 子 Agent 顺手改了需求/设计文档 | 越权；流程要求人类点头（约束 2） |
| 为省事把「完成定义」写成「实现完毕」 | 不可验证 = 无法验收 |
| 只让子 Agent 跑单测、不跑玩家视角检查 | 会漏掉宿主装配缺口（本项目已发生 6 次） |
