### L-2 事件池的作用域是「地点」而非「场景」

选项的 `goto` 只切场景、**不更新 `currentLocation`**；而事件池按 `pool.locate(area, location)` 过滤候选。
后果：在 `town_gate` 场景里推进时间，评估的是**旧地点**（如 market）的事件——目标事件永不入选。
宿主侧的补法是显式 `moveTo` 一次（L2 检查的 `syncLocationTo` 即此）。

**待入档**：这是**作者与宿主都会踩**的坑，应写进 detail-design §4.4（事件池）与开发者规范。
**→ 状态：待处理**（#10 的 i18n 条目与事件池作用域同属「设计文档待补」，
但本次 5 条修订提案未含本项——留待 M2 收尾的反思报告一并处理，理由见下）。

### L-3 窄窗口 + 高 `moveCost` 的时段对齐问题

地点移动消耗 `moveCost` 个时段。神龛的 `moveCost = 2`，而事件窗口是 `night`（slotIndex 3）——
逐次推进的步长为 2，只能在**同奇偶**的时段间跳，可能永远碰不到目标窗口。
作者写窄窗口事件时须核算该地点的 `moveCost` 奇偶性。

**待入档**：内容编写规范（事件窗口 × 地点消耗的配合）。
**→ 已于 2026-09-27 落档**（detail-design §4.4「窄窗口 × 地点 `moveCost` 的时段对齐」，经人类审查同意）。

### L-4 检查自身的坑（供后续写检查的人参考）

写 L2 检查时踩到的三处，均与「引擎的正确行为」有关，不是缺陷：

1. **`advanceSlots` 会自动清场事件** → 用「当前场景」判定事件是否触发会误判为「没触发」；
   正确口径是看**事件打断记录**（触发过即算）；
2. **`__time.advance` 要求 `slots ≥ 0`** → 「倒拨时钟」不可行，只能向前推进（跨天绕行）；
3. **`advanceSlots` 的原地推进**（位置不变 → 不触发导航）才是「纯时间流逝」的正确写法。

### L-5 检查工具的「口径」必须与被测系统一致（否则产生假阳性）

**事件**：原 T-2 记录的「`showIf` 可见性缺陷」经 2026-09-26 复核**不成立**——
选项实际被正确隐藏。误报根因：L2 检查的驱动层 `route-driver.ts` 的 `choices()`
返回 `session.choices.map((c) => c.id)`，**未过滤 `hiddenByFilter`**；而渲染层
`OptionList` 会过滤。检查据此断言「选项可见」，与被测系统**不同口径**。

**为什么危险**：假阳性会驱动「修一个不存在的问题」，浪费工作量并污染结论；
这次是在用户过目环节被拦下，若直接派发就会让子 Agent 去改一个正确的实现。

**防线**：
- 检查工具暴露的读取面**默认采用被测系统的用户可见口径**（如 `choices()` 只返回可见项），
  需要原始面时另给显式命名的方法（`rawChoices()`）；
- 凡「可见性」断言，须在用例注释里写明用的是哪个口径；
- 已登记为 `docs/develop.md` 约束 8 的补充条目（待人类审查后落笔）。

**元教训**：这是同类问题的第 2 次（首次即 T-2 的原始误判本身）。检查层建设到一定规模后，
**检查工具自身也需要被检查**——尤其是「读取面口径」这类隐蔽差异。

### L-6 门禁的**覆盖面**也会出现盲区（不只是口径）

**事件**（2026-09-27 发现）：根 `pnpm typecheck` 是 `pnpm -r typecheck`（递归跑各包的
同名脚本），而 `apps/player-demo` 与 `apps/editor-app` 的 `package.json` **没有
`typecheck` 脚本** → **两个应用从未被类型检查**。`vite build` 不做类型检查，CI 也拦不住。

**实证后果**：`apps/player-demo/src/main.tsx` 的 `PANEL_TITLES: Record<PanelId, string>`
缺 `shop` / `battle` / `history` 三项（`PanelId` 在 17/16/25B 增加了这些成员），
`tsc` 直接报 TS2739——该编译错误在 `main` 上**藏了数周**。已修复（补脚本 + 补成员）。

**共性**：这与 L-5（口径差异）是一类问题的两个面——**门禁「跑了什么」和「怎么读」都可能有盲区**。
`pnpm -r <script>` 的覆盖面取决于**每个包是否声明了该脚本**，「某包漏声明」是静默的。

**防线建议**：
- 凡用 `pnpm -r` 组织的门禁脚本，应有一条**覆盖面断言**（如断言 workspace 内每个
  可执行包都声明了必需脚本），而不是依赖「大家都记得加」；
- 本次案例可作为 `docs/develop.md` 约束 11 的**第三个实例**（前两个：T-2 读取面口径、
  #12 环境装配面）——建议在规范里把「门禁覆盖面」也纳入「同口径」范畴。
