### 1.2 两次违规的共同形态

- **都在 `main` 工作区上直接编辑 + `git add` + `git commit`**，未先 `git checkout -b`；
- **都是「小改动」**：第 1 次是审查报告 §6/§7 更新（+48/−6 行，单文件），

  仍然复发。

### 1.3 检查体系为何没拦住

| 防线 | 现状 | 为何失效 |
|---|---|---|
| `docs/develop.md` 约束 9 | 文字明示「main 分支禁止直接提交」 | 纯文字约定，**执行期无任何机械拦截**；AI 在长会话/压缩后不会重新阅读 |
| GitHub branch protection | **未配置** | develop.md 自述：「本仓库当前无 GitHub branch protection（操作账号非仓库 admin）」——已登记的事实约束 |
| CI | `on: push: branches: [main]` 会跑 | CI 是**事后**检查：它验证「代码对不对」，不判断「该不该走 PR」——直提的 commit 同样能让 CI 全绿 |
| PR 流程 | CI 全绿 + 自审清单 | 只在「确实开了 PR」时生效；直提路径**完全绕过**该流程 |

**结论**：约束 9 是当时十条约束中**唯一一条「有明确规则、却完全没有机械化检查」的工程约束**。
其余工程约束（5/6/7/8/10）在 2026-09-15 的整改中都已配有可执行检查
（计划四节结构由模板保证、覆盖率阈值、content-graph 五检、validateArg、wiring-check、验收路径断言），
约束 9 却停留在文字层——**复发不是偶然，是检查覆盖的不对称**。

### 1.4 为什么「更努力地记住」不是解

- 第 2 次违规发生在**摘要明确记录过该承诺**之后，说明「记忆/自律」在上下文压缩面前不可靠；
- 长会话中「小改动」的任务心智（改一行）与「流程心智」（开分支→PR→CI→合入）竞争时，
  前者默认获胜——除非流程成本被工具降到接近零，或违规被工具直接拒绝。

## 2. 根因分析

**直接原因**：AI 在 `main` 工作区上直接提交（两次）。

**根本原因**：约束 9 只有文字定义，**没有机械兜底**。规则的正确性早已被确认，
缺的是「让违反规则的操作在物理上无法完成（或成本显著升高）」的那一层。

**为什么既有检查没拦住**（本条对应约束 3 的触发条件 2「同类缺陷重复出现」）：

- 既有检查全是**产物检查**（代码正确性、内容连通性、文档一致性），
  **没有一条是流程检查**；
- 流程正确性此前被假定为「执行者的自觉」——而本项目的执行者主要是 AI，
  其自觉随上下文状态波动，这是结构性事实，不是偶发失误。

## 4. 已落地的修复（机械化兜底）

| 产物 | 作用 | 验证 |
|---|---|---|
| `.githooks/pre-commit` | 在 `main`/`master` 上提交时**拒绝**并打印正确流程 | `fixtures/helpers/test/git-hooks-guard.test.ts` 3 例（拒绝/放行/`--no-verify` 通道） |
| `.githooks/pre-push` | 向 `main`/`master` 推送时**拒绝**（发布期兜底；`--no-verify` 提交也拦得住） | 同上 2 例（拒绝 + 远端未被写入 / 功能分支放行） |
| `scripts/setup-git-hooks.mjs` + `package.json` 的 `prepare` | `pnpm install` 时自动 `git config core.hooksPath .githooks`，新人/新环境零配置获得保护 | 测试在临时仓库实测脚本效果（2 例） |
| `=` 文件清理 | 删除 `4c2e263` 误入库的 0 字节重定向产物 | `git rm --cached` + 删除 |

设计说明：

- **钩子目录入库**（`.githooks/`）而非写入 `.git/hooks/`（后者不入库、无法分发）；
- **测试是行为测试**：在临时 git 仓库中真实执行 commit/push 并断言**被拒 + 产物未产生**
  （而非断言脚本文本包含某字符串）；
- **紧急通道保留**：两处钩子均支持 `--no-verify`，但 develop.md 要求绕过须在 PR/反思报告说明原因；
- **与 CI 的关系**：钩子是**提交期/发布期**防线，CI 仍是**合入期**防线，二者互补；
  钩子可被 `--no-verify` 绕过，因此 CI 与人工审查不可省。

### 4.1 落地过程中发现的第二个坑：POSIX 可执行位（本 PR 内修复）

守卫本身在首次 CI 运行时就踩了一次同类陷阱，值得单独记录：

- **现象**：PR #21 首轮 CI 失败——`git-hooks-guard.test.ts` 中两条「应被拒绝」的用例
  在 Linux runner 上断言失败（commit/push 居然成功了）。
- **根因**：POSIX 平台的 git **只执行带可执行位的钩子文件**，无位则静默忽略
  （仅打印 `hint: ... ignoredHook`）。两处踩中：
  1. 测试夹具用 `copyFileSync` 复制钩子（默认权限 0644）→ 钩子被忽略；
  2. 更严重的是**入库产物本身**：本仓库在 Windows 开发（`core.filemode=false`），
     `git add` 把钩子记为 `100644`——即使测试夹具修好，Unix/CI 侧的真实守卫仍是死的。
- **证据**（WSL 实测，同一脚本 0644 vs 0755 对照）：

  ```
  A: 0644 → commit SUCCEEDED (hook ignored - reproduces CI bug)
  B: 0755 → commit rejected (guard works on POSIX)
  ```

- **修复**：
  1. `git update-index --chmod=+x .githooks/pre-commit .githooks/pre-push`（入库为 `100755`）；
  2. 测试夹具补 `chmodSync(target, 0o755)`；
  3. 新增回归断言：`.githooks/` 下不得存在 `100644` 模式的钩子文件。
- **教训**：「有守卫」不等于「守卫生效」——幂等性/权限/静默忽略这类
  **平台相关失效模式**，只有跨平台实测（或 CI 上的真实执行）才能暴露；
  这与本项目 11 个缺陷「模块内正确、跨环境失配」的形态一致。

  应回到本节重新评估该推论。
