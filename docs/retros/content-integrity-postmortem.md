| 项 | 内容 |

## 1. 事实清单（经执行验证，非推测）

以下每一条都用引擎实际运行确认过（Node 侧宿主装配 + 浏览器实测）。

### 1.1 事件：10 条全部不会触发

**证据**：`createGameHost` 构造 `TimePipeline` 时只配置了 3 个步骤：

```ts
// packages/runtime-ui/src/app/game-host.ts:362
return new TimePipeline({
  runtime: rt,
  config: timeConfig,
  statusTick: createItemTickProvider(),
  npcSchedule: createNpcScheduleProvider(timeConfig),
  questDeadline: createQuestDeadlineProvider(),
  // ← 缺 eventEval（步骤 6：事件池评估）
});
```

`TimePipelineOptions` 声明了 6 个可选步骤（`statusTick` / `bodyRevert` / `npcSchedule` /
`eventEval` / `questDeadline` / …），**全部可选、缺省静默跳过**。引擎侧 10 号事件系统
已完整实现且有性能基准测试，但宿主没接线，因此 `ev_wall_whisper`、`ev_market_rumor`、
`ev_ferry_greeting` 等 10 条事件在 demo 中**一次也不会进入评估**。

### 1.2 `npc.<id>.met` 是只读视图，且引擎从不置为 true

**证据**：全引擎搜索 `met: true` 的写入路径 → **零命中**。`met` 只在两处被写成 `false`
（`newGameState` 建档、`favor` 指令建档）：

```ts
// packages/engine/src/effects/builtins/relations.ts:35
record = { favor: 0, met: false, flags: {} };
```

而 fixture 中有 **7 处条件依赖 `npc.<id>.met`**，全部因此永久为假：

| 位置 | 条件 | 后果 |
|---|---|---|
| `events.yaml` ev_wall_whisper | `npc.old_guard.met` | 事件永不满足触发条件 |
| `events.yaml` ev_ferry_greeting | `npc.ferryman.met` | 同上 |
| `events.yaml` ev_trail_wanderer | `npc.ferryman.met` | 同上 |
| `areas/riverside.yaml` warehouse 解锁 | `npc.ferryman.met \|\| flag.warehouse_open` | 只剩 flag 一路可用（勉强不算死） |
| `quests/hillside_survey.yaml` acceptIf | `npc.ferryman.met && insight >= 3` | 任务永远不可接取 |
| `scenes/riverside_ferry.yaml`（段落/选项 showIf） | `!met` / `met` | 首次/再次文本永远停在"首次" |

> **这是引擎能力缺口，不是数据错误**：设计 §4.6 提到 `npc.<id>.met` 并把它列为表达式
> 变量域，但 §3.3 的效果指令表里**没有任何"标记已遇见"的写入口**（`set` 只接受
> `attr/flag/counter` 与 `npc.<id>.flags.<名>`）。于是这个字段成了只读且恒假。

### 1.3 第 3 区域（hillside）整块不可达

**证据**：全包 `goto` 目标集合中**没有任何跳转指向 `hillside_trailhead`**。
`hillside_trailhead` 的文件注释写着「由河堤上堤道进入」，但 `riverside_embankment`
的选项只有 `to_ferry` / `to_town`——**入口从未被接上**。

后果：hillside 的 6 个场景、3 条事件、`hillside_survey` 任务线的全部现场**都无法抵达**。

### 1.4 任务、结局、商店都没有触发入口

| 内容 | 应有入口 | 实际 |
|---|---|---|
| `wall_rubbing` | 某场景调用 `quest: {action: accept}` | **零调用** → 永远停在 `undiscovered` |
| `hillside_survey` | 同上 | **零调用**（且 `requires: [wall_rubbing]`，前者也不 done） |
| `quiet_town` 结局 | 某场景调用 `ending` | **零调用** → 永远不触发 |
| `market_stall` 商店 | 某场景进入商店 | **零调用** → 不可见 |
| 成就 `first_rumor` / `sharp_eye` | 18 号成就系统 | 未实现（0 文件），且宿主未接 |

### 1.5 一个已修复的具体缺陷（作为对照）

`riverside_ferry` 的 `talk_ferryman` 首条效果原写作 `set: { key: 'npc.ferryman.met', value: true }`。
`set` 的 key 形态校验在 **execute（运行期）** 才执行：

```ts
// packages/engine/src/effects/builtins/state.ts:70
throw instructionError(op, `NPC 记忆 key 需为 'npc.<id>.flags.<名称>' 形态，实际 '${key}'`, { key });
```

该选项因此**必然抛 `EFFECT_FAILED`**（浏览器实测：点击"上前搭话"无反应、选项列表清空）。
已修复为 flag 域表达（commit `3706fe5`）。

### 1.6 浏览器实测的现场表现（与用户观察一致）

| 用户看到的现象 | 实际原因 |
|---|---|
| 走到河畔渡口后点"上前搭话"没反应 | 1.5 的 `set` 语法错误（已修） |
| 事件从不发生 | 1.1 宿主未接事件系统 + 1.2 `.met` 恒假 |
| 任务日志一直空 | 1.4 无 `quest: accept` 调用 |
| 后山区域进不去 | 1.3 无入口 |
| 剧情"好像没写完" | 上述叠加：**场景内选项分支是通的，场景外的系统层全部断线** |

## 2. 根因分析：检查体系缺了什么

这一节回答「为什么这些缺陷通过了 2287+ 测试、CI 四门禁、以及我自己的验收」。

### 2.1 缺「加载期指令语义校验」

**现状**：`set` 的 key 形态、`favor` 的 NPC 存在性、`advance_time` 的 cost 合法性等
**只在运行期校验**（在指令的 `execute` 里）。加载器（06 号）在 `walk.ts` 只收集三类东西：
`refKind` 引用、`exprSchema` 表达式、`call` 扩展调用；`cross-ref.ts` 只核对"引用的目标是否存在"。

**后果**：一条语法非法的效果指令，能让包**加载期零诊断通过**（`diagnostics = []`，
我的审查报告还把它当作健康信号），直到玩家点到那个选项才炸。

**缺口**：设计 §7.7 列了 12 条校验规则，但**没有一条覆盖"效果指令参数语义"**
（规则清单里有 `dangling-jump` / `dangling-ref` / `expr-compile`，唯独没有 `invalid-instruction-arg`）。

### 2.2 缺「内容可达性」检查

**现状**：`crossRef` 检查的是**正向引用完整性**——"跳转目标是否存在"。
完全没有**反向可达性**——"这个场景/事件/任务/结局有没有入口能到达"。

**后果**：
- 孤儿场景（无人 goto 到的非事件场景）不会被发现
- 区域无入口（hillside）不会被发现
- 任务无接取调用、结局无触发调用、商店无入口，全部不会被发现
- 事件写了但永不满足条件（`.met` 恒假），不会被发现

**这是我这次最该被机制拦住的一类**：我写了 20 个场景、10 条事件、2 条任务，
`validate-docs` 全绿、loader 零诊断、2289 测试全绿——**但没有任何检查回答"玩家能走到吗"**。

### 2.3 缺「接线完整性」检查

**现状**：`TimePipeline` 的 6 个步骤、`SceneRunner` 的可选注入、`EffectRegistry` 的
可选依赖（`items`/`npcs`/`quests`/`eventPool`/`mediaResolver`/`timeConfig`）**全部可选且缺省静默**。

**后果**：「引擎能力已实现但宿主没接」这类问题**没有任何信号**。10 号事件系统有完整
测试和性能基准，但宿主没传 `eventEval` —— 引擎不会警告，测试不会红，CI 不会红。

**设计层面的对比**：引擎对"数据错误"是显性化的（悬空引用报 error、缺文本键报 warning），
但对"接线缺失"是静默的。**同一个项目里两种标准不一致**，而后者更隐蔽（数据看得见，接线看不见）。

### 2.4 缺「E2E 断言深度」要求

**现状**：我的 E2E 用例（`e2e/player-flow.spec.ts`）断言的是**元素可见性**：

```ts
await expect(page.locator('[data-choice="talk_ferryman"]')).toBeVisible();   // ← 只到"看得见"
await expect(page.locator('[data-choice="to_fish_market"]')).toBeVisible();
```

**从没点下去验证结果**。所以 `talk_ferryman` 点击抛 `EFFECT_FAILED` 完全漏网——
测试报告"3/3 通过"，而实际那个按钮是坏的。

**更严重的对照**：M1 计划 §11 第 3 条明确要求
「走通新游戏 → 推进时间 → **触发事件** → **任务推进** → 存/读档 → 内容过滤生效」，
而我的 E2E 只覆盖了「新游戏 → 跨区域 → 语言切换 → IndexedDB」——
**明确要求的事件触发与任务推进两项，我一项都没测**。

### 2.5 一个「顺从性」失误：把完整性断言改弱

**现状**：夹具扩充后，12 处硬编码规模断言（`toHaveLength(5)`、`toBe(1)`）变红。
我当时的处理是**改成下界断言**：

```ts
// 改前（完整性信号）
expect(definition.areas.size).toBe(1);
// 改后（只保证不退化，不保证完整）
expect(definition.areas.size).toBeGreaterThanOrEqual(3);
```

**当时的理由**是「内容会持续扩充，精确断言是负资产」（这个理由本身成立），
**但代价是我同时丢掉了"内容块是否接上"的守卫**——现在即使某个区域整个没入口，
这些断言也照样绿。**正确做法应是分两层**：规模用下界，**连通性用独立的结构断言**
（例如"从 entryScene 做 BFS 必须覆盖全部区域的至少一个地点"）。

### 2.6 缺「内容流测试」这一层

**现状**：测试体系有三层——单元（模块内）、组件（UI）、E2E（浏览器冒烟）。
**缺一层**：「内容图测试」——用引擎加载器 + 宿主装配，在 Node 里**遍历内容图**，
断言"从 entryScene 出发可达全部区域"、"每条事件至少有一个场景能触发它"、
"每条任务都有 accept 入口"、"每个结局都有触发点"。

这类测试成本极低（不需要浏览器，秒级），却能覆盖本次全部 4 个断点。

### 2.7 检查覆盖矩阵（现状 vs 应有）

| 维度 | 当前谁在查 | 覆盖 |
|---|---|---|
| 数据结构合法性（schema） | Zod + fixture 测试 | ✅ 完整 |
| 引用目标存在（正向） | loader crossRef | ✅ 完整 |
| 指令参数语义 | **无人**（运行期才炸） | ❌ **缺** |
| 内容可达（反向） | **无人** | ❌ **缺** |
| 宿主接线完整 | **无人** | ❌ **缺** |
| 交互结果正确 | E2E（只测可见性） | ⚠️ **浅** |
| 里程碑验收路径覆盖 | 人工（我做得不完整） | ⚠️ **漏** |

### 4.1 建议新增约束 7 —— 内容连通性

- **内容扩充必须过连通性检查**：新增区域/场景/事件/任务/结局时，必须有以下自动化证据：
  1. 从 `manifest.entryScene` 做图遍历，**能到达全部区域的至少一个场景**；
  2. **每条事件**至少有一个可达场景或时段能满足其触发条件（静态可判的部分）；
  3. **每条任务**在可达内容中至少存在一个 `quest: accept` 调用点；
  4. **每个结局**至少存在一个 `ending` 触发点；
  5. **每个商店**至少存在一个入口。
- **落点**：`packages/engine/test/loader/` 新增 `content-graph.test.ts`（Node 秒级，进 CI 门禁）；
  编辑器校验中心（26 号）后续复用同一规则集（DD-12）。

### 4.2 建议新增约束 8 —— 加载期指令语义校验

- **效果指令的参数语义必须在加载期校验**，不得延后到运行期：
  1. `set`/`add` 的 `key` 形态（含 `npc.<id>.flags.<名>` 四段规则）；
  2. `favor`/`reputation` 的目标实体存在性；
  3. `give`/`take`/`wear` 的物品存在性与类型匹配（garment 才能 wear）；
  4. `quest` 的 questId 与 action 合法性；
  5. `goto`/`ending`/`battle` 的目标存在性（前两者已由 crossRef 覆盖，需扩展到指令参数面）。
- **落点**：loader 的 `compile` 或新增 `validateEffects` 步骤调用各指令的**参数语义校验器**
  （可复用指令注册表的 schema + 新增 `validateArg` 钩子）；error 级诊断进 `diagnostics`。
- **配套**：设计 §7.7 的规则清单补 `invalid-instruction-arg`、`unreachable-content` 两条。

### 4.3 建议新增约束 9 —— 宿主接线完整性

- **引擎可选能力被宿主忽略时必须显式化**：
  1. `TimePipeline` 的每个可选步骤，构造时若缺失且**游戏包中存在对应数据**（如包内有
     `events.yaml` 却未接 `eventEval`）→ 运行时告警（`console.warn` + 调试面板可见）；
  2. 宿主装配必须提供 `assertWiring()` 之类的自检，在 `start()` 时对"包内有数据但未接线"
     的情形报出**可诊断告警**；
  3. 25 号宿主测试补"接线完备性"用例（构造含事件的包 → 断言 `eventEval` 存在）。
- **理由**：与引擎既有的"数据错误显性化"标准对齐——**同项目内两种标准不应不一致**。

### 4.4 建议修订约束 5 —— 里程碑验收路径

- 七项自检第 6 项「验收 demo」**从"实测"细化为"路径覆盖"**：
  1. 必须逐条勾选里程碑计划中列出的验收路径（M1：新游戏 → **推进时间** → **触发事件** →
     **任务推进** → 存/读档 → **内容过滤生效**），每条附可复现步骤与观察结果；
  2. **未覆盖的路径必须显式登记为"未验证"**，不得以"E2E 通过"笼统代替；
  3. E2E 用例**必须断言交互结果**（状态变化 / 场景跳转 / 文本更新），
     **禁止只断言元素可见性**——"按钮存在"不等于"按钮可用"。

### 4.5 建议补充开发流程细节（可并入约束 2 或 4）

- **规模断言与连通性断言分层**：规模变化用下界断言（可扩充），
  **内容块连通性必须有独立断言**，不得因规模断言放宽而失去完整性守卫。
- **设计文档与实现对账**：凡设计文档提到的能力（如 `npc.<id>.met`），
  实现期必须验证"是否有写入路径"；**只读且永假的字段不得进入 fixture 条件**——
  发现此类字段应回写设计（能力缺口）而非照抄使用。
