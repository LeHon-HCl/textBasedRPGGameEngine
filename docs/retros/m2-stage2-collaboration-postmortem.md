### 1.2 三次「险些造成损失」的事件（均已闭环）

**事件 A：driver 撞车（#34 vs #33）**
B 方在 #34 提出新写 `battle/driver.ts` 做交互式会话驱动器；A 方 #33 已交付同职能的
`createBattleController`（B 方写提案时 #33 尚未入 main）。**发现时两者都尚未合入**，
经 A 方在 #34 review 中说明后，B 方撤回提案（`JumpTarget.branches` 提案同样撤回）。
若未在合入前对齐，将产生两份功能重叠的驱动器——**这是分工文档「先认领」规则覆盖不到的
盲区：认领只防重复认领，不防「不同工作包内实现同一能力」**。

**事件 B：误合 PR #31（修复前 commit）**
A 方执行 `gh pr merge`（未带 PR 号，意图合入自身分支）时，gh CLI 按当前分支推断，
误合了 #31 的**修复前 commit**，导致 main 门禁转红（lint: non-null assertion），
而修复 commit 留在未合入分支上。处置：立即开 #32 补上修复，main 恢复绿链。
**根因：合并命令未显式指定 PR 号 + 未在合并前看 CI 结论。**

**事件 C：两次在 main 上直接写改动**
A 方两次在先前的 main 工作区残留未提交改动（PR #32 合入后未切分支即继续开发），
均被 `.githooks/pre-commit` 拦截（约束 9 的机械化兜底**两次都正常工作**），
随后切分支规范提交。**结论：约束 9 的 hook 是有效的最后一道防线，但「切完 main
立即开分支」尚未成为肌肉记忆。**

## 2. 根因分析

### 2.1 「先认领后动工」的边界模糊（事件 A）

分工文档 §3 规则 5 写「W0 合入前，W1/W2/W4/W5 只能认领不能开工」，但未规定
**跨工作包的能力重叠**如何处置。A 方在 W0 review 未完成时即开工 W1/W2
（理由：文件所有权清晰、不阻塞对方），B 方按自身理解提案补充驱动器能力。

**根因**：分工文档防的是「同一工作包被两人认领」，而实际风险还有一类——
「**不同工作包各自实现同一能力**」（A 的接线层与 B 的驱动器、分支参数的两条通道）。
这类风险的检测点在**接口讨论**而非文件所有权。

### 2.2 合并操作缺少机械约束（事件 B）

`gh pr merge` 在不带 PR 号时按当前分支推断行为，属 CLI 语义陷阱；
且合并时机（CI 结论未出）无规则约束。

**根因**：约束 9 规定了「禁止直接向 main 提交」，但**未规定「合并 PR 的操作规程」**
（显式 PR 号、CI 绿后合并、合并前确认目标）。

### 2.3 阶段二的协作成本结构

| 环节 | 成本 | 评价 |
|---|---|---|
| 分工文档 + 认领表 | 1 个 PR | 低投入高回报（零重复劳动） |
| 接口冻结（W0） | 2 commit | 关键路径但价值最大（零返工） |
| 双向 review | 6 次 | 发现 3 项设计悬空（若留到合入后成本 ×5+） |
| 跨线 additive 变更说明 | 2 次 | 必要沟通成本 |

**结论：协作机制在「防重复」上完全达成目标，在「防重叠设计」上依赖人的自觉。**

## 4. 改进建议（待人类裁定）

### 建议 1：分工文档模板增补「能力重叠检查」（防事件 A 复发）——**已采纳**，落 `docs/plans/collaboration-template.md` §0 规则 2

在 `docs/plans/M2-stage2-battle-split.md` 的规则部分（后续阶段的分工文档沿用）增补：

> **开工前检索义务**：认领工作包前，须检索 ① main 上是否已有同职能模块
> （`git log --oneline main -- <目录>` + 目录实际内容）；② 开放 PR 的标题与描述中
> 是否包含同职能关键词。发现疑似重叠 → 在对应 PR/issue 提出，**先对齐后动工**。

### 建议 2：develop.md 增补「PR 合并规程」（防事件 B 复发）——**已采纳**，落 `docs/develop.md` 约束 9

建议在约束 9 下增补：

> **合并规程**：合并 PR 必须显式指定 PR 号（`gh pr merge <number>`），
> **禁止**在合并命令中省略 PR 号（gh CLI 会按当前分支推断，存在误合风险）；
> 合并前必须确认 ① 目标 PR 的 CI 结论为绿（`gh pr checks <number>`）；
> ② 本地已 checkout main 或准备在合并后立即同步。里程碑收尾的合并由人类执行或人类在场。

### 建议 3：契约变更的通报升级为「清单项」（低优先级）——**已采纳**，落 develop.md PR 自审清单 + 模板 §0 规则 5

当前跨线契约变更依赖 PR 评论（#33 两次 additive 变更均如此通报，运作良好）。
建议在分工文档的 PR 自审清单中固化一行：「本次是否修改对方所有权文件或公共契约？
是 → 是否已在 PR 描述中列明变更点与影响？」——把惯例变成检查项。

### 建议 4：固化「公共契约先冻结 + 文件所有权表」（成功经验）——**已采纳**，落 `docs/plans/collaboration-template.md` §0 规则 4 + §3

阶段二的成功要素建议写入分工文档模板，供阶段三+复用：
① 公共类型文件先行冻结（W0），变更走 additive + 对方确认；
② 文件所有权表逐文件到人，跨所有权改动必须走对方 review；
③ 每个工作包「认领表 + draft PR 占位」双记录，先到先得可追溯。
