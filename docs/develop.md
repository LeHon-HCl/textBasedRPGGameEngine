# 开发流程规范（develop.md）

> 本文档约束 TextGameEngine 所有开发活动（AI 代理与人类协作者）。与根目录 `AGENTS.md`
> 冲突时，以更严格者为准。
> 生效日期：2026-09-13（2026-09-15 修订：约束按「文档 ＞ 代码」重要性重排编号；
> 新增文档审查点头、反思报告、内容连通性、加载期完整性四类约束）。
> 修订须走标准 PR 流程，且**文档类修订须经人类审查点头**（约束 2）。

## 十条核心约束

**编号即重要性**：文档层约束（1–4）优先于工程层约束（5–10）。理由见约束 1。

---

## 第一部分：文档层（最重要）

### 约束 1 —— 维护文档 ＞ 维护代码

**文档是产品的一部分，不是附属品。** 项目对外的可理解性、可验收性、可传承性全部依赖文档；
代码可以重写，文档承载的判断与约束丢了就找不回来。

文档是人工验收代码的重要桥梁，**必须正确反映项目状态**：

- 代码变更时同步更新对应文档，与代码同一 PR 交付：
  - 新增/修改子系统、指令、管线步骤、依赖关系 → 更新 `docs/architecture.md`（见其「维护规则」一节）；
  - 完成子任务 → 勾选 `docs/tasks/NN-*.md` 对应项；模块完成 → 勾选 `docs/tasks/progress.md`；
  - 行为语义变更（超出原设计）→ 先改 `docs/proposal.md` 或 `docs/detail-design.md` 并单独提交，再落代码。
- 提交前运行 `node scripts/validate-docs.mjs` 确保文档门禁通过。

**文档层级与读者**（新增文档前先确认它该放哪一层）：

| 层级 | 文档 | 读者与用途 | 更新时机 |
|---|---|---|---|
| 入口 | `README.md` | 新人 / 外部协作者：这是什么、怎么跑起来 | 里程碑状态变化、命令/结构变化 |
| 需求 | `docs/proposal.md` | 需求基线：FR/NFR 编号定义处、决策 D1–D15 | **需求变更时（须单独提交）** |
| 设计 | `docs/detail-design.md` | 设计意图：§x.y 接口签名、DD-* 决策 | **设计变更时（须单独提交）** |
| as-built | `docs/architecture.md` | 实现者 / 审查者：数据流、子系统索引 | 代码结构变化（见其 §8 维护规则） |
| 任务 | `docs/tasks/NN-*.md` | 模块子任务清单与完成定义 | 模块开发中持续勾选 |
| 进度 | `docs/tasks/progress.md` | 里程碑与模块状态（唯一登记处） | 模块完成 / 里程碑审查通过 |
| 审查 | `docs/reviews/MN-review.md` | 里程碑例行验收记录 | 里程碑审查时 |
| 反思 | `docs/retros/*-postmortem.md` | 异常事件的深度复盘与改进结论 | 事件发生后（见约束 3） |
| 流程 | `docs/develop.md`（本文件） | 协作者：核心约束与 PR 流程 | 流程本身变更时 |

**禁止**：同一事实在两处维护（必然漂移）。需要引用时用链接或编号指向权威处。

### 约束 2 —— 文档修订须人类审查点头

**凡对权威文档的修订，必须先获得人类明确点头，再落笔。**

- **适用范围**：`docs/proposal.md`（需求）、`docs/detail-design.md`（设计）、
  `docs/develop.md`（本文件）、`docs/architecture.md` 的结构性变更，
  以及 `docs/tasks/*.md` 中**任务范围的增删**（勾选完成项不在此列）。
- **流程**：
  1. 提出修订方案（改哪一节、改成什么、为什么），**以人类可读的形式呈现**（对话或计划文档）；
  2. **等待人类明确同意**（"可以改" / "按这个改"）；未获同意不得直接修改；
  3. 修订单独成 commit（Conventional Commits，`docs(...)` 前缀），PR 正文标明「经人类审查同意（日期）」。
- **例外**：拼写/链接修复、格式规范化、事实性数字更新（如测试用例数）可自行修订，
  但须在 PR 正文注明「属免审类型」。
- **理由**：文档是判断的载体（约束 1）。AI 自行修订权威文档，等于把「判断」降格为
  「AI 的单方面决定」——一旦判断有误，错误会被固化成后续所有工作的前提。

### 约束 3 —— 反思报告（异常事件必须留档）

**当某事件暴露出「检查体系有盲区」或「需要对文档体系做较大调整」时，必须产出反思报告。**

- **触发条件**（任一）：
  1. 缺陷通过全部既有检查（单测 / CI / 审查）仍逃逸到人工验收阶段；
  2. 发现**同类缺陷重复出现**（说明上次的修复没触及根因）；
  3. 发现约束文档/设计文档自身有缺口或自相矛盾；
  4. 里程碑审查发现「模块都完成了但目标未达成」。
- **位置**：`docs/retros/<主题>-postmortem.md`（用途与格式见 `docs/retros/README.md`）。
- **内容要求**：事实清单**必须可复现**（附命令、代码位置、实测输出），不得写推测性结论；
  须包含「根因分析（为什么既有检查没拦住）」与「改进建议（要改哪条约束/加什么检查）」。
- **与约束 2 的关系**：反思报告只做归因与建议；由它引发的文档修订**仍须人类审查点头**。
- **理由**：不写反思报告，同一个盲区会以不同形式反复出现——「修了 bug 但没修检查」
  是这类项目的典型失败模式。

### 约束 4 —— 文档归档

**过时文档不删除，归档**（保留决策溯源），但必须显式标注其失效：

- 位置：`docs/archive/`，文件名可读化（如 `prompt-autonomous-agent-protocol.md`）。
- **文首必须**写明：归档状态与日期、取代者（哪个文档）、仍有效部分去哪找。
  `validate-docs.mjs` 会校验该标注存在（缺失即红）。
- 归档文档**从门禁的必需文档列表中移除**（它不再生效，不应阻塞 CI）。
- 归档不等于放任漂移：若其中内容仍被引用，说明取代文档有缺口——应补取代文档，
  而不是让引用指向归档件。

## 第二部分：工程层

### 约束 5 —— 计划约束

一切开发计划（里程碑计划、模块计划、修复计划）**必须**严格按以下四节组织，缺一不可：

1. **开发目标**：做什么、达成什么可观察的结果。
2. **影响面**：涉及哪些包/模块/文档/夹具，可能破坏什么既有行为。
3. **commit 拆分**：列出每个 commit 的内容与边界（默认粒度：一个子任务 = 一次 commit）。
4. **验收效果**：可执行的验收标准（测试断言、门禁命令、人工验收步骤）。

不满足四节结构的计划不得进入实现阶段。

### 约束 6 —— 质量约束

**严格 TDD**：

- 每个子任务先写**失败测试**（红），再写实现使其通过（绿），必要时重构。
- 交付前全量测试与 lint 必须全绿；未通过不算完成。
- 修 bug 时必须先写一个能复现该 bug 的失败测试，再修复（禁止试错式打补丁）。
- **测试为防缺陷而写，不为指标而写**。判断「该不该补一个测试」的标准是「这条路径出错的
  代价是否值得一个断言」，不是「覆盖率数字够不够」。为拉高百分比而写的测试是负资产：
  占用时间、增加维护面，还会制造「已被测试覆盖」的假安全感。

**覆盖率的定位（它是底线，不是目标）**：

- **测的什么**：`vitest` V8 provider 原生插桩采集、经 AST 重映射为源码语义的
  **语句 / 分支 / 函数 / 行**四类覆盖——即「测试执行期间这些代码被跑到过没有」。
- **判定口径**：按 glob **聚合**（`vitest.config.ts` 的 `thresholds`），非逐文件。
  单个文件的覆盖洼地会被平均值掩盖，**不要用聚合数字为某个文件的质量背书**。
- **不能证明什么**（重要）：覆盖率只能说明「没被跑过的地方一定有风险」，**不能说明
  「跑过的地方是对的」**。11 号模块的 `attr.<id>` 漏映射 `derived` 缺陷，语句与行覆盖
  都是 100% 但逻辑是错的——覆盖率抓不到逻辑错误、抓不到错误路径的语义正确性、
  也抓不到需求是否被正确实现。
- **已知边界**：统计范围含 Node 单元测试与 jsdom 组件测试；E2E 不计入覆盖率但
  作为里程碑验收的独立证据（约束 10）。
- **结论**：阈值作为**防退化的底线**存在（跌破即 CI 红），**不作为补测试的驱动指标**；
  禁止为达标而写空测试。

**断言分层（规模 vs 完整性）**：

- **规模断言用下界**（内容会持续扩充，精确计数是负资产）：
  如 `expect(areas.length).toBeGreaterThanOrEqual(3)`。
- **但结构完整性必须有独立断言**——放宽规模断言时，**必须同时补一条结构断言**
  守护「内容块是否接上」，否则整块内容会失去入场守卫。
  反例：把 `toHaveLength(1)` 改成 `toBeGreaterThanOrEqual(3)` 而不补结构断言，
  会导致「某区域整个没有入口」也照样绿。
- 结构断言的形态：关键成员存在性（`toContain('riverside')`）、
  集合等价（`toEqual(['hillside','old_town','riverside'])`）、
  关系不变量（目录名 == `scene.area`）；连通性断言见约束 7。

**分级注释规范**：

- **必须注释**：所有导出符号与公共 API——JSDoc，说明用途与约束（不变量、副作用、抛错条件）。
- **必须注释**：复杂局部变量——魔法值、非自明的中间结果、绕开直觉的逻辑分支。
- **不强制**：自明的局部变量。禁止为「下一行在做什么」写噪音注释。
- 注释使用中文；技术术语与代码标识符保留原文。

### 约束 7 —— 内容连通性

**内容数量达标 ≠ 内容可玩。** 新增/修改区域、场景、事件、任务、结局、商店时，
必须提供**连通性证据**（自动化，非人工目测）：

| # | 检查 | 通过标准 |
|---|---|---|
| 1 | 区域可达 | 从 `manifest.entryScene` 做图遍历，能到达**每个区域的至少一个场景** |
| 2 | 事件可触发 | **每条事件**至少有一个可达场景/时段能满足其触发条件（静态可判部分） |
| 3 | 任务可接取 | **每条任务**在可达内容中至少存在一个 `quest: accept` 调用点 |
| 4 | 结局可达成 | **每个结局**至少存在一个 `ending` 触发点 |
| 5 | 商店可进入 | **每个商店**至少存在一个入口 |

- **级别**：连通性缺失按 **error 级**处理（与悬空引用同级，阻断加载/门禁）——
  不可达的内容等于不存在，且会掩盖缺陷（写了却不触发的事件给人「已实现」的错觉）。
- **落点**：`packages/engine/test/loader/` 下按内容图组织（Node 秒级，进 CI 门禁）；
  26 号编辑器校验中心复用同一规则集（DD-12）。
- **豁免**：允许显式标记「预留内容」（`reserved: true` 之类），但须在反思报告或 PR
  中说明用途；**不得以"以后会接"为由长期豁免**。

### 约束 8 —— 加载期完整性

**能在加载期发现的问题，不得留到运行期。**

1. **效果指令参数语义必须在加载期校验**（不得只靠 execute 内的运行期检查）：
   - `set`/`add` 的 `key` 形态（含 `npc.<id>.flags.<名>` 四段规则）；
   - `favor`/`reputation` 的目标实体存在性；
   - `give`/`take`/`wear` 的物品存在性与类型匹配（garment 才能 `wear`）；
   - `quest` 的 questId 与 action 合法性；
   - `goto`/`ending`/`battle` 的目标存在性（从字段面扩展到**指令参数面**）。
2. **宿主接线完整性**：
   - 引擎的可选能力（`TimePipeline` 各步骤、`EffectRegistry` 各可选依赖等）
     在**包内存在对应数据却未接线**时，必须给出**可诊断告警**（不得静默跳过）；
   - 宿主装配须提供接线自检（启动时对「包内有数据但未接线」报出告警）；
   - 对应模块的宿主测试须包含「接线完备性」用例。
3. **设计对账**：设计文档提到的能力字段，实现期必须验证**存在写入路径**；
   **只读且永假的字段不得进入 fixture 条件**——发现即回写设计（能力缺口），不得照抄使用。
4. **理由**：与引擎既有的「数据错误显性化」标准对齐——同一项目内不应存在两种标准；
   「写错了但加载通过、玩家点到才炸」是最难排查的一类缺陷。

### 约束 9 —— git 主线保护

**main 分支禁止直接提交**。一切改动（含文档）按以下顺序进行：

```
git checkout -b <type>/<slug>   # 从最新 main 切出，如 feat/09-time-system
   ↓
开发（严格 TDD，子任务粒度 commit）
   ↓
git push -u origin <branch>
   ↓
gh pr create                     # PR 正文附 AI 自审清单（见下）
   ↓
review：AI 自审 checklist + CI 全绿（lint / test / coverage / build+typecheck / validate-docs）
   ↓
gh pr merge --rebase --delete-branch   # 保持线性历史，保留子任务粒度 commit
```

- 分支命名：`<type>/<模块号>-<slug>`，如 `feat/09-time-system`、`docs/dev-process`、`fix/07-resolver-fallback`。
- commit 规范：Conventional Commits + 任务编号，沿用现有格式 `feat(engine): xxx（09 任务 A1）`。
- 本仓库当前无 GitHub branch protection（操作账号非仓库 admin），主线保护靠本约定自律；
  **里程碑收尾由用户人工验收把关**作为兜底（约束 10）。
- 若合入后发现问题，修复同样走新分支 + PR，禁止 force push main。
- **合入后收尾**：确认远端分支已删除（rebase 合入有时不会自动删），残留分支及时清理。

### 约束 10 —— 里程碑审查

**里程碑不是「模块做完了」，而是「审查通过」**。模块级完成判定见各任务书的「完成定义」；
里程碑级达成判定必须走本节流程：

```
模块全部完成 → 执行者自检（下表七项）→ 输出审查报告 → 用户人工验收 → 通过后勾选 progress.md
```

**自检清单**（提交审查前逐项跑，报告里贴证据而非结论）：

| # | 检查项 | 命令 / 方法 | 通过标准 |
|---|---|---|---|
| 1 | 全量测试 | `pnpm exec vitest run --root .` | 全绿，记录文件数/用例数 |
| 2 | 覆盖率 | `pnpm test:coverage` | shared ≥ 90%、engine ≥ 80%（四指标） |
| 3 | 静态检查 | `pnpm -w lint && pnpm -w build && pnpm -w typecheck` | 全绿 |
| 4 | 文档一致性 | `node scripts/validate-docs.mjs` | 全绿（含架构文档覆盖全部已实现子系统） |
| 5 | 文档对账 | 人工比对 `architecture.md` 与 `ls packages/engine/src/` | 无「已实现但未登记」或「已登记但已删除」 |
| 6 | 验收 demo（**路径覆盖**） | 逐条执行里程碑计划列出的验收路径（见下） | **每条路径附可复现步骤与观察结果**；未覆盖项必须显式登记为「未验证」 |
| 7 | 遗留登记 | 检查各任务书「实现记录」段与 PR 风险段 | 已知妥协全部有记录与后续计划 |

**第 6 项的细化要求（验收 demo = 路径覆盖，不是笼统"跑一遍"）**：

- 必须**逐条勾选**里程碑计划中列出的验收路径。以 M1 为例：
  新游戏 → 推进时间 → **触发事件** → **任务推进** → 存/读档 → **内容过滤生效**；
- 每条路径附「可复现步骤 + 观察结果」；**未覆盖的路径必须显式标为「未验证」**，
  **不得以「E2E 通过」笼统代替**（一条 E2E 用例覆盖不了未写的路径）；
- **E2E 必须断言交互结果**（状态变化 / 场景跳转 / 文本更新），
  **禁止只断言元素可见性**——「按钮存在」不等于「按钮可用」；
- 涉及跨系统的路径（事件触发、任务推进）必须**端到端验证到可观察结果**，
  不得以「引擎侧单测已覆盖」代替集成验证。

**审查报告格式**（写入 `docs/reviews/MN-review.md`，并在 progress.md 里程碑段链接）：

```markdown
## M1 里程碑审查报告（YYYY-MM-DD）

### 交付范围
<模块列表与各自 PR 编号>

### 门禁证据
<七项自检的实测输出摘要；覆盖率贴具体数字，测试贴文件数/用例数>

### 验收路径覆盖
<逐条勾选里程碑计划的验收路径；每条附可复现步骤与观察结果；
 未覆盖项显式标为「未验证」并说明原因>

### 对账结果
<architecture.md vs 代码结构的一致性核对结论；文档与代码的已知偏差及处置>

### 遗留与风险
<已知妥协、未实现的设计条目、后续模块的依赖影响>

### 验收结论
[ ] 待人工验收  [ ] 通过  [ ] 有条件通过（附条件）
```

**约束**：里程碑审查由**用户人工验收判定**，AI 不自行宣布里程碑达成（约束 9 兜底条款）。
审查通过后，在 `progress.md` 勾选该里程碑并在其下写入验收记录（含日期与验收方式）。

## PR 自审清单模板

每个 PR 正文附带以下清单，逐项勾选：

```markdown
## AI 自审清单
```
